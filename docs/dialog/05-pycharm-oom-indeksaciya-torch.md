# 05. Повторный OOM в PyCharm: дело было в индексации torch

**Дата:** 2026-10-08

## Что сообщил пользователь

```
The IDE ran out of available memory.
Please consider increasing the value of "Maximum Heap Size" setting
```

## Поправка к этапу 04

На этапе 04 причиной была названа работа **инспектора переменных** PyCharm
с тензором `x_train` на 150 МБ. Лог опроверг это предположение: разбор
ниже показывает, что куча кончалась на **индексации `torch`**, а не на
инспекторе. Гипотеза этапа 04 была догадкой, проверить ее тогда было нечем -
лог не читался.

## Разбор по логу

Восстановленная хронология из `~/Library/Logs/JetBrains/PyCharm2025.2/idea.log`:

| Время | Событие |
|---|---|
| 18:18:13 | `HeapDumpSnapshotRunnable - Capturing heap dump` - OOM при лимите 2 ГБ |
| 18:26:55 | пользователь прописал `-Xmx4096m` |
| 18:26:58 | перезапуск PyCharm |
| 18:26:59 | в логе `JVM options: [... -Xmx2048m ... -Xmx4096m ...]` - новый лимит применился |
| 18:27:00 | начата индексация, в очереди 3851 файл |
| 18:28:03 | `OutOfMemoryError: Java heap space` - **снова OOM, уже на 4 ГБ** |
| 18:28:22 | `FileBasedIndexImpl - Java heap space` - падает именно индексатор |

Ключевое: сообщение, которое прислал пользователь, - это **не разбор
старого дампа**, а новый OOM. Первая версия объяснения на этом этапе
предполагала обратное (PyCharm действительно показывает похожий текст при
разборе дампа на следующем старте), и это предположение тоже было снято
логом.

## Почему падает индексатор

Замеры по проекту:

| Что | Сколько |
|---|---|
| `.venv` целиком | 1.0 ГБ, 39249 файлов, 9037 из них `.py` |
| `torch` в site-packages | 583 МБ |
| `torch/_C/_VariableFunctions.pyi` | 1.1 МБ **одним файлом** |
| `torch/_VF.pyi` | 1.1 МБ одним файлом |

Состояние проекта в PyCharm на момент падения (`.idea/MNIST.iml`):

```xml
<excludeFolder url="file://$MODULE_DIR$/.venv" />
<orderEntry type="jdk" jdkName="Python 3.13 virtualenv at .../MNIST/.venv" />
```

То есть `.venv` **уже исключена** из индексации как содержимое проекта -
это не та проблема. Но она назначена интерпретатором, а значит PyCharm
индексирует ее site-packages как **библиотеку SDK**. Сборка стабов по
гигантским `.pyi` файлам `torch` и съедает кучу.

Усугубило то, что ноутбук 02 запускался одновременно с первичной
индексацией, сразу после открытия проекта: в `recentProjects.xml` открытым
файлом записан `02_linear_softmax_manual.ipynb`, а OOM наступил через 75
секунд после старта IDE. Индексация torch и Jupyter-сессия сложили пики.

## Состояние памяти машины

Здесь тоже была допущена ошибка в оценке и исправлена замером.

| Показатель | Значение |
|---|---|
| всего RAM | 18 ГБ |
| `vm_stat` свободные страницы | 0.2 ГБ |
| `memory_pressure`, свободно по системе | **51%** |
| swap | 2.1 ГБ использовано из 3 ГБ |
| RSS PyCharm | 2.66 ГБ |

На этапе 04 по `vm_stat` было сделано заключение, что памяти критически
мало. Это неверно: на macOS свободные страницы - не тот показатель,
система держит в RAM кеш. Правильный показатель `memory_pressure` дает
51% свободно. Памяти достаточно, поднимать лимит кучи безопасно.

## Что сделано

1. **Лимит кучи поднят с 4 до 6 ГБ.** Записан
   `~/Library/Application Support/JetBrains/PyCharm2025.2/pycharm.vmoptions`
   с единственной строкой `-Xmx6144m`. Предыдущая версия сохранена рядом
   как `pycharm.vmoptions.bak-20261008-183059`.

   Проверено по логу, что пользовательский файл **дополняет** дефолт
   приложения, а не заменяет: в `JVM options` присутствовали оба значения
   `-Xmx` (дефолтное 2048 и пользовательское 4096), выигрывает последнее, а
   `-XX:+HeapDumpOnOutOfMemoryError` и `-XX:ReservedCodeCacheSize=512m` из
   дефолта остались в силе. То есть короткий пользовательский файл ничего
   важного не теряет.

2. **Раздел в `README.md` переписан** под настоящую причину: было про
   инспектор переменных, стало про индексацию torch. Добавлены признаки
   принадлежности ошибки (JVM против Python-ядра), предупреждение не
   запускать ноутбук одновременно с первичной индексацией, и четвертое
   решение - снять интерпретатор проекта, чтобы индексировать было нечего.

## Что должен сделать пользователь

Перезапустить PyCharm (новый лимит читается только при старте) и **дать
индексации доучиться, не запуская ноутбук одновременно**. Это разовая
плата: после построения индекса проблема не возвращается.

Если OOM повторится и на 6 ГБ - значит индексация torch на этой машине
нерентабельна, и остается решение 3 из README: снять интерпретатор
проекта, а ноутбуки запускать через `.venv/bin/jupyter notebook`.

## Вывод на будущее

Два предположения на этапе 04 (инспектор переменных как причина, нехватка
RAM по `vm_stat`) оказались неверны, и оба снялись одной проверкой - чтением
`idea.log` и `memory_pressure`. Лог IDE надо читать сразу, а не строить
гипотезы по тексту сообщения: он содержит точное время, точный лимит,
точный компонент, который упал.
