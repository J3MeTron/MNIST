# 04. PyCharm падала с heap dump на ноутбуке 02

**Дата:** 2026-10-08

## Что сообщил пользователь

При запуске второго ноутбука PyCharm выдала:

```
Heap dump has been created at .../heapDump-pycharm-1791472693840.hprof.
It will be analyzed next time you start PyCharm.
```

## Первая развилка диагностики

Сообщение про heap dump относится к **JVM самой PyCharm**, а не к
Python-ядру. Python-процесс при нехватке памяти ведет себя иначе: его либо
убивает система, либо он падает с `MemoryError`, и никаких `.hprof` при
этом не появляется. То есть кончилась память у IDE.

Отсюда две гипотезы, которые надо было разделить замерами:

1. ноутбук отдает гигантский вывод, и PyCharm давится его рендерингом;
2. ноутбук держит большие объекты, и давится инспектор переменных PyCharm.

## Замеры

### Объем вывода ноутбука 02

| Что | Сколько |
|---|---|
| весь текстовый вывод всех ячеек | 5.0 КБ |
| все картинки matplotlib (5 фигур) | 0.27 МБ |
| самая тяжелая картинка (матрица ошибок) | 103 КБ |

Гипотеза 1 отпадает: такой вывод не способен переполнить ничего.

### Память Python-ядра

Пик RSS при полном прогоне настоящим ядром:

| Ноутбук | Пик RSS |
|---|---|
| 01 | 235 МБ |
| 02 | 711 МБ |
| 03 | 726 МБ |
| 04 | 935 МБ (обучает сеть дважды: с momentum и без) |

Для Python это норма: из них порядка 250 МБ - сам импорт `torch`,
150 МБ - `x_train` формы (50000, 784) в float32, остальное - копии при
конвертации и промежуточные тензоры.

### Конфигурация JVM PyCharm

```
-Xms256m
-Xmx2048m
-XX:+HeapDumpOnOutOfMemoryError
```

Пользовательского `pycharm.vmoptions` нет, то есть действует дефолт
приложения: **предел кучи 2 ГБ**. Флаг `HeapDumpOnOutOfMemoryError` и есть
то, что создало дамп. Размер дампа на диске - 896 МБ.

## Вывод

Подтверждена гипотеза 2. В сессии живет тензор `x_train` на 150 МБ одним
объектом; инспектор переменных PyCharm строит представления объектов
сессии на стороне JVM, и 2 ГБ кучи на это не хватает. Ноутбук при этом
корректен: прогон тем же ядром вне PyCharm проходит целиком.

Важно, что это **не лечится со стороны ноутбука**. Данные MNIST нужны
целиком, 150 МБ - их физический размер, уменьшать нечего.

## Что сделано

1. **Гигиена памяти в ноутбуках 02-04.** Третий набор из архива (test,
   10000 примеров) распаковывался в `_` и оставался в памяти до конца
   сессии - распаковка кортежа создает ссылку, и сборщик мусора его не
   трогает. Добавлены `del _` и `gc.collect()`.

   **Честная оценка эффекта: примерно 31 МБ из 700, то есть это не
   решение проблемы, а устранение ненужного объекта.** Замер до и после:
   684 МБ против 711 МБ, разница в пределах разброса между запусками.
   Польза в другом: в сессии больше не висит крупный объект, который
   инспектору переменных незачем показывать.

2. **В ноутбук 02 добавлен вывод размера данных в МБ.** Чтобы было видно,
   какой объект в сессии самый крупный, и почему именно он создает
   проблемы IDE.

3. **В `README.md` добавлен раздел про heap dump** с тремя решениями:
   запуск мимо PyCharm через `.venv/bin/jupyter notebook`, поднятие кучи
   до 4 ГБ через `Help -> Change Memory Settings`, отключение инспектора
   переменных.

## Рекомендация пользователю

Для этих ноутбуков PyCharm как среда запуска - не лучший выбор: ее
Jupyter-интеграция держит представления объектов в JVM с лимитом 2 ГБ, а
задача по своей природе работает с сотнями мегабайт тензоров. Надежнее
`.venv/bin/jupyter notebook notebooks/` или Colab. PyCharm остается удобна
для `run.py` и модулей `src/` - там ноутбучного инспектора нет и проблема
не возникает.

## Вывод на будущее

Сообщение об ошибке надо сначала атрибутировать процессу. `.hprof`,
`OutOfMemoryError`, упоминание heap - это JVM, то есть IDE. `MemoryError`,
`Killed`, `ModuleNotFoundError` - это Python-ядро. Лечение у них разное, и
попытка чинить ноутбук при проблеме IDE потратила бы время впустую.
