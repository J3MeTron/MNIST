# 01. Уточнение решений: четыре развилки

**Дата:** 2026-10-08

Перед началом работы ассистент задал три вопроса, где разные ответы вели к
разному объему работы. Четвертая развилка (шаг обучения) всплыла уже при
прогоне кода и решена без вопроса, по результатам замеров.

---

## Развилка 1: насколько "вручную" делать обратный проход

**Варианты:**

| Вариант | Что это значит |
|---|---|
| A. Autograd + ручные формулы рядом | градиенты считает `backward()`, но каждая величина продублирована выведенной на бумаге формулой и проверена на равенство |
| B. Полностью вручную, без autograd | `requires_grad` не используется совсем, backward написан сам |
| C. Оба варианта последовательно | сначала A, потом B |

**Выбрано: A.**

**Основание.** Вариант A дает и математику, и навык работы с PyTorch:
видно, как формула выглядит на бумаге, и видно, как ее же считает
библиотека. Вариант B дает математику, но учит писать код, который в
реальной работе никто не пишет. Вариант C - двойной объем при небольшой
добавке к пониманию.

**Чем компенсирована потеря.** Чтобы вариант A не превратился в
"autograd все посчитал, а формулы написаны для вида", сверка встроена
в сам цикл обучения через `assert`: ручные формулы проверяются каждые 200
шагов на всем протяжении обучения, и расхождение прерывает обучение
исключением. Плюс добавлена третья независимая проверка - конечными
разностями.

## Развилка 2: архитектура

**Варианты:** только линейная 784-10; сразу MLP 784-128-10; линейная,
потом MLP.

**Выбрано: линейная, потом MLP.**

**Основание.** В линейной модели вся цепочка градиента - два шага
($\partial L/\partial Z$, потом через линейный слой), и ее можно разобрать
целиком, не отвлекаясь на цепное правило. MLP добавляет ровно одну новую
идею - проход через нелинейность. Если начинать сразу с MLP, эти две вещи
смешиваются.

Побочная польза: линейная модель упирается в 92%, и на ее примере видно
**почему** нужен скрытый слой, а не просто "так принято". У линейной
модели веса еще и интерпретируются напрямую - столбец $W[:,k]$ смотрится
как картинка 28x28, то есть шаблон цифры. У MLP такой наглядности уже нет.

## Развилка 3: структура проекта под Colab

**Варианты:** только ноутбуки; только `.py` плюс тонкая обертка-ноутбук;
ноутбуки плюс модули плюс журнал диалога.

**Выбрано: ноутбуки плюс модули плюс журнал.**

**Основание.** Требования конфликтуют: Colab хочет самодостаточный `.ipynb`,
PyCharm хочет `.py` для отладки с точками останова. Решено не выбирать, а
закрыть оба:

* **ноутбуки самодостаточны** - ни один не импортирует `mnist_manual`,
  все нужное определено в его собственных ячейках. Любой можно открыть в
  Colab по отдельности, ничего не подключая. Это главный учебный материал;
* **модули `src/mnist_manual/`** - тот же код, разложенный по файлам, с
  CLI. Для запуска из PyCharm, отладки и повторного использования.

**Сознательная цена этого решения - дублирование кода** между ноутбуками и
модулями, и между ноутбуками 02 и 03 (ноутбук 03 переопределяет функции из
02). Альтернатива - импорты - сломала бы работу в Colab и заставила бы
прыгать между файлами при чтении. Для учебного проекта читаемость
важнее отсутствия дублей; в рабочем коде выбор был бы обратным.

## Развилка 4: шаг обучения (решена замерами)

У преподавателя `lr = 0.5`. При прогоне оказалось, что на этом значении
точность на валидации **колеблется**, а не растет монотонно:

| Модель | lr | Точность по эпохам, % |
|---|---|---|
| линейная | 0.5 | 91.39 - 90.32 - 89.78 - 91.18 - 92.50 |
| MLP | 0.5 | 95.29 - 95.22 - 97.16 - 97.65 - **93.34** |
| MLP | 0.3 | 94.38 - 96.01 - 96.76 - 97.14 - **94.99** |
| линейная | 0.1 | 90.89 - 91.53 - 91.81 - 91.94 - 92.29 |
| MLP | 0.1 | 92.04 - 94.70 - 95.40 - 96.11 - 95.72 |

На `lr = 0.5` шаг перелетает минимум: видно по провалу MLP на пятой эпохе
с 97.65% до 93.34%.

**Выбрано: `lr = 0.1`, 10 эпох** как значение по умолчанию для обеих
моделей. Монотонность важнее скорости: на колеблющейся кривой студент не
поймет, учится модель или нет.

Проверка, что это не баг: на `lr = 0.1` ошибка на обучающих батчах падает
монотонно (максимум ошибки за эпоху: 2.37, 0.66, 0.48, 0.47, 0.37, 0.43,
0.37, 0.34, 0.31, 0.26), а колебания точности в пределах 0.5% остаются на
трех разных seed - то есть это шум SGD, а не ошибка в коде.
