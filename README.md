# MNIST вручную на тензорах PyTorch

Учебный проект: классификация рукописных цифр MNIST, собранная из базовых
тензорных операций - без `torch.nn` и без `torch.optim`. Все градиенты
выведены на бумаге, выписаны формулами и проверены против autograd и против
конечных разностей.

Курс "Алгоритмы нейронных сетей", магистратура ВГУ.

## Результаты

| Модель | Параметров | Точность на валидации | Ошибок из 10000 |
|---|---|---|---|
| Линейная 784-10 | 7 850 | 92.43% | 757 |
| MLP 784-128-10 (ReLU) | 101 770 | 97.42% | 258 |
| Тот же MLP через `nn.Module` | 101 770 | 97.20% | 280 |
| MLP + momentum 0.9 | 101 770 | 97.66% | 234 |

Условия: SGD, `batch_size=64`, `lr=0.1`, 10 эпох, `seed=0`. Валидация -
10000 примеров, которых модель не видела при обучении.

Ручная реализация и штатная через `nn.Module` дают одинаковую точность в
пределах шума SGD. Это и есть главный вывод проекта: за вызовами библиотеки
нет ничего, кроме разобранных формул.

## Запуск локально (PyCharm)

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
```

В PyCharm: `Settings -> Project -> Python Interpreter -> Add -> Existing`,
указать `.venv/bin/python`.

В PyCharm **дополнительно** надо выбрать этот же интерпретатор как ядро в
самом ноутбуке (селектор сверху справа) - PyCharm держит эти два выбора
отдельно. Если не выбрать, ноутбук пойдет на системном Python, где `torch`
нет, и упадет на первой ячейке.

Запуск без PyCharm:

```bash
.venv/bin/jupyter notebook notebooks/
```

Модели можно обучать и без ноутбуков, через CLI:

```bash
python run.py                                   # линейная, 10 эпох
python run.py --model mlp                       # MLP 784-128-10
python run.py --model mlp --epochs 3 --lr 0.2
python run.py --help                            # все параметры
```

`run.py` - обертка, которая добавляет `src` в путь поиска модулей. В
PyCharm достаточно нажать Run на этом файле; флаги задаются в
`Run -> Edit Configurations -> Parameters`.

Параметры CLI: `--model {linear,mlp}`, `--epochs`, `--batch-size`, `--lr`,
`--hidden`, `--seed`, `--log-every`, `--check-grads-every`, `--data-dir`.
Флаг `--check-grads-every 0` отключает сверку ручных градиентов
(по умолчанию - каждые 200 шагов).

## Если ноутбук не запускается

Содержимое ноутбуков проверено прогоном под настоящим ядром Jupyter, поэтому
почти все отказы при запуске - это окружение, а не код. Три типовые причины
по тексту ошибки.

### `ModuleNotFoundError: No module named 'torch'`

Самая частая. Ноутбук исполняется интерпретатором, в котором нет `torch`.
В системном Python его и не должно быть - все зависимости стоят в `.venv`.

**Лечение в PyCharm:**

1. `Settings -> Project -> Python Interpreter`
2. шестеренка -> `Add` -> `Existing environment`
3. указать `.venv/bin/python` внутри папки проекта
4. **в самом ноутбуке** сверху справа выбрать тот же интерпретатор:
   PyCharm держит выбор ядра для ноутбука отдельно от интерпретатора проекта,
   и это легко пропустить
5. перезапустить ядро: `Run -> Restart Kernel`

**Проверка, что интерпретатор правильный** - выполнить в первой ячейке:

```python
import sys
print(sys.executable)      # должен указывать внутрь .venv
import torch
print(torch.__version__)
```

### PyCharm не стартует Jupyter-сервер

Если `.venv` создавалась до появления в `requirements.txt` пакетов для
ноутбуков, в ней нет `notebook` и `ipykernel`. Доставить:

```bash
.venv/bin/pip install -r requirements.txt
```

Запуск без PyCharm, если проще:

```bash
.venv/bin/jupyter notebook notebooks/
```

### PyCharm падает с heap dump или "The IDE ran out of available memory"

Это **не ошибка ноутбука**. Переполнилась куча JVM самой PyCharm, а не
Python-ядра. Признак принадлежности: `.hprof`, `OutOfMemoryError: Java heap
space`, слово heap - это JVM, то есть IDE. У Python-ядра ошибки другие:
`MemoryError`, `Killed`, `ModuleNotFoundError`.

**Настоящая причина - индексация `torch`, а не ноутбук.** Когда `.venv`
назначена интерпретатором проекта, PyCharm индексирует ее site-packages как
библиотеку SDK. В `torch` 583 МБ и такие файлы, как
`torch/_C/_VariableFunctions.pyi` на 1.1 МБ одним файлом - сборка стабов по
ним и съедает кучу. Дефолтных 2 ГБ не хватает, 4 ГБ тоже может не хватить.

Вывод самого ноутбука к этому отношения не имеет: он весит 5 КБ текста и
0.27 МБ картинок. Python-ядро тоже ведет себя нормально, замеренный пик
RSS: 235 МБ на ноутбуке 01, около 700 МБ на 02-03, 935 МБ на 04 (он
обучает сеть дважды).

**Что усугубляет:** запуск ноутбука одновременно с первичной индексацией
сразу после открытия проекта. Индексация torch и Jupyter-сессия складывают
пики. После того как индекс построен один раз, проблема не повторяется.

**Решение 1, самое надежное - запускать мимо PyCharm:**

```bash
.venv/bin/jupyter notebook notebooks/
```

Ядро то же, кода менять не надо, JVM в схеме вообще не участвует. Тот же
эффект дает Colab.

**Решение 2 - поднять память PyCharm:**

`Help -> Change Memory Settings` -> **6144 МБ** -> `Save and Restart`.
4096 МБ на индексации torch может не хватить (проверено: падало и на нем).

Это пишет пользовательский файл
`~/Library/Application Support/JetBrains/PyCharm<версия>/pycharm.vmoptions`.
Он **дополняет** дефолт приложения, а не заменяет: остальные флаги
(`-XX:+HeapDumpOnOutOfMemoryError`, `-XX:ReservedCodeCacheSize=512m`)
остаются в силе, а из двух значений `-Xmx` выигрывает последнее, то есть
ваше.

После перезапуска **дать индексации доучиться, не запуская ноутбук
одновременно** - прогресс виден в строке состояния. Это разовая плата.

**Решение 3 - не индексировать torch вообще:** снять интерпретатор проекта
(`Settings -> Project -> Python Interpreter -> No interpreter`) и
пользоваться PyCharm как редактором, а ноутбуки запускать через
`.venv/bin/jupyter notebook`. Пропадет автодополнение по `torch`, зато
индексировать будет нечего.

**Решение 4, вспомогательное:** перезапускать ядро между ноутбуками, чтобы
тензоры предыдущего не оставались в сессии, и отключить панель переменных
над ноутбуком.

### Ошибка в самом Colab

В Colab `torch` и `matplotlib` предустановлены, ставить ничего не нужно.
Если падает ячейка загрузки данных - это сеть: `mnist.pkl.gz` (16 МБ)
качается с github.com. Перезапустить ячейку.

Если падает последняя ячейка ноутбука 04 с сообщением про недоступные
модули проекта - это **ожидаемо и не ошибка**: ячейка сама это сообщает и
на остальной ноутбук не влияет. Ноутбуки 01-03 модули проекта не
используют вообще.

### Если ничего из этого не подошло

Нужен точный текст ошибки и номер ячейки: без них причину не определить,
потому что сами ноутбуки проходят прогон целиком.

## Что именно сделано вручную

| Что | Как в проекте | Чем заменяется в обычном коде |
|---|---|---|
| объявление параметров | `torch.randn(...) / sqrt(n_in)`, `requires_grad_()` | `nn.Linear` |
| прямой проход | `x @ W + b`, `z.clamp(min=0)` | `layer(x)`, `F.relu` |
| функция потерь | `nll(log_softmax(z), y)` | `nn.CrossEntropyLoss` |
| градиенты | формулы в `grads.py` + сверка с `backward()` | только `backward()` |
| шаг спуска | `p -= lr * p.grad` под `no_grad()` | `optimizer.step()` |
| обнуление градиентов | `p.grad.zero_()` | `optimizer.zero_grad()` |
| нарезка на батчи | `torch.randperm` + срезы | `DataLoader` |

Autograd используется (это выбранный подход, см.
[`docs/dialog/01-utochnenie-resheniy.md`](docs/dialog/01-utochnenie-resheniy.md),
развилка 1), но каждая его величина продублирована ручной формулой.
Сверка встроена в цикл обучения через `assert` и срабатывает каждые 200
шагов, то есть формулы проверяются на всем протяжении обучения, а не
только в начальной точке.

### Ключевые формулы

| Что | Формула |
|---|---|
| softmax | $p_k = e^{z_k - m} / \sum_j e^{z_j - m}$, где $m = \max_j z_j$ |
| перекрестная энтропия | $L = -\frac{1}{B}\sum_n \log p_{n, y_n}$ |
| градиент по логитам | $\partial L/\partial Z = (\mathrm{softmax}(Z) - Y)/B$ |
| линейный слой | $\partial L/\partial W = X^\top G$, $\ \partial L/\partial b = \mathrm{sum}(G, 0)$, $\ \partial L/\partial X = G W^\top$ |
| ReLU | $\partial L/\partial Z = (\partial L/\partial H) \odot [Z > 0]$ |
| шаг SGD | $p \leftarrow p - \eta\, \partial L/\partial p$ |

Выводы - в [`docs/theory.md`](docs/theory.md).

## Данные

`mnist.pkl.gz` из репозитория туториалов PyTorch - тот же файл, что в
ноутбуке преподавателя. Внутри три набора: train (50000), valid (10000),
test (10000, в проекте не используется).

Картинки уже развернуты в векторы длины 784 и нормированы в диапазон
[0, 1]. Нормировка обязательна: при значениях пикселей 0..255 логиты
получились бы порядка сотен, и softmax переполнился бы на первом шаге.

`torchvision.datasets.MNIST` сознательно не используется - он тянет лишнюю
зависимость и прячет данные за слоем `Dataset`/`DataLoader`, а для разбора
нужен сырой тензор `(N, 784)`.
